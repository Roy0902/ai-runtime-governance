Ownership rules:

- Controllers translate HTTP only. They do not contain policy, crypto or
  transaction boundaries.
- Application services own one transaction per use case. A controller never opens
  a transaction across an upstream wait.
- Domain records/enums hold invariants that must not depend on Spring.
- Repositories are the only SQL owners. No controller or domain object uses JDBC.
- Crypto services never log inputs or outputs.
- The frontend never re-implements validation that the server owns; it mirrors
  copy and field hints only.
- Generated API types are read-only and regenerated by `npm run ai:contract`.

## 4. Persistence model (V1)

All identifiers are UUIDs. Timestamps are `timestamptz` in UTC. Secrets are never
stored raw.

| Table | Key columns | Invariant |
|---|---|---|
| `account` | `id`, `email` (normalized), `password_hash`, `email_verified_at`, `status` (`PENDING`/`VERIFIED`/`DISABLED`), `mfa_state` (`NONE`/`PENDING`/`ENROLLED`/`RECOVERY_REQUIRED`), `scope_id`, `gateway_entitlement`, `version` | Unique normalized email; `scope_id` unique and immutable once set |
| `web_session` | `id`, `token_hash`, `context` (`ANONYMOUS`/`SETUP`/`HUMAN`), `account_id`, `purpose`, `csrf_hash`, `created_at`, `last_activity_at`, `absolute_expires_at`, `idle_expires_at`, `recent_auth_at`, `recent_auth_expires_at`, `state` | Token hash unique; HUMAN/SETUP rows require an account; rotation ends the old row |
| `confirmation_link` | `id`, `account_id`, `purpose` (`VERIFY`/`RESET`), `token_hash`, `created_at`, `expires_at`, `consumed_at`, `superseded_at` | Partial unique: one current link per account/purpose |
| `mail_request` | `id`, `account_id`, `address`, `purpose`, `link_id`, `state`, `attempts`, `next_attempt_at`, `last_error_class` | At most 100 uncompleted; one active send globally |
| `enrollment_operation` | `id`, `account_id`, `purpose` (`INITIAL_ENROLLMENT`/`RECOVERY_ENROLLMENT`/`AUTHENTICATOR_REPLACEMENT`/`RECOVERY_CODE_GENERATION`), `state`, `candidate_seed_id`, `recovery_set_id`, `created_at`, `expires_at`, `verified_at`, `completed_at`, `cancelled_at`, `superseded_at`, `version` | One pending operation per account/purpose |
| `totp_seed` | `id`, `account_id`, `state` (`PENDING`/`ACTIVE`/`RETIRED`), `key_id`, `nonce`, `ciphertext`, `representation_version`, `activated_at`, `retired_at` | One ACTIVE seed per account |
| `recovery_code_set` | `id`, `account_id`, `state` (`PENDING`/`ACTIVE`/`REVOKED`), `created_at`, `expires_at`, `activated_at`, `revoked_at` | One ACTIVE set per account |
| `recovery_code` | `id`, `set_id`, `verifier`, `consumed_at` | Ten codes per set; one committed consumption |
| `totp_used_step` | `account_id`, `time_step`, `accepted_at` | Primary key `(account_id, time_step)` |
| `rate_event` | `id`, `bucket_type`, `bucket_key`, `occurred_at` | Rolling window source of truth |
| `rate_bucket_state` | `bucket_type`, `bucket_key`, `last_seen_at` | At most 10,000 source and 10,000 identity buckets |
| `failed_auth_event` | `id`, `identity`, `occurred_at` | 15-minute rolling history; unknown addresses included |
| `failed_auth_state` | `identity`, `cooldown_until`, `last_seen_at` | Cooldown only, never a permanent flag |
| `host_audit` | `id`, `occurred_at`, `operator_id`, `action`, `target_account_id`, `reason`, `outcome`, `changed_fields`, `correlation_id` | Append-only; no secret fields |
| `seed_key_metadata` | `key_id`, `state` (`INACTIVE`/`ACTIVE`/`RETAINED`/`RETIRED`), `created_at`, `activated_at` | One ACTIVE key; retained backup until matched restore |

Flyway owns the schema. The test harness migrates from empty for every run; no
manual DDL is permitted.

## 5. Crypto design

| Concern | Design |
|---|---|
| Password hash | PBKDF2-HMAC-SHA256, 210,000 iterations, 16-byte salt, 32-byte output, self-describing `$pbkdf2-sha256$i=...` string (DR-051; supersedes the former Argon2id v19 profile) |
| Predecessor | PBKDF2-HMAC-SHA256 at 100,000 iterations; verify then rehash to current on successful full auth; compare-and-set on `account.version` so a concurrent reset wins (DR-051) |
| Recovery verifier | `SHA-256("arg-recovery-v1" || len(accountId) || accountId || len(setId) || setId || codeBytes)`; constant-time compare; never adaptive hashing |
| TOTP seed | AES-256-GCM, 12-byte nonce, 16-byte tag, AAD `accountId|seedId|representationVersion`; key id is metadata |
| Opaque tokens | 32 bytes from `SecureRandom`, base64url (43 chars); store only SHA-256 hash |
| TOTP | RFC 6238, HMAC-SHA1, 6 digits, 30-second step, current ±1; replay blocked by `totp_used_step` insert |
| Randomness | `SecureRandom`; no `Math.random`, `Random`, time-seeded or UUID-as-secret |
| Comparison | `MessageDigest.isEqual` for verifiers and token hashes |

Key provisioning is an operator action. The application loads the active key from
a deployment-local protected source, never from source code, logs or the database
ciphertext. Missing key affects only key-dependent operations.

## 6. Transaction boundaries

| Use case | One transaction contains | Must not contain |
|---|---|---|
| Register | account insert (if new), mail_request, link issuance | SMTP send |
| Verify consume | link lock/consume, `email_verified_at`, SETUP session rotation | mail send |
| Setup access | credential check, SETUP session rotation | TOTP verification |
| Start/restart enrollment | operation supersession, seed/recovery-set creation | secret display after commit (returned once) |
| Complete enrollment | operation lock, TOTP check, seed activation, recovery-set activation, scope creation, HUMAN rotation | SMTP |
| Sign-in | credential/factor verification, used-step insert, session creation, cooldown clear | upstream calls |
| Password change | recent-auth check, hash update, other-session revocation, current rotation | mail |
| Replacement/regeneration | operation lock, factor/set swap, other-session revocation, current rotation | mail |
| Reset consume | link lock/consume, password update, all-session revocation | mail |
| Host command | state change + `host_audit` insert | any HTTP request |

A transaction never spans an SMTP/network call. Mail is a durable row plus a
worker.

## 7. Request pipeline

```text
request
  -> correlation id
  -> JSON/size/content-type validation
  -> origin + CSRF validation (state-changing methods)
  -> browser-context resolution (cookie hash, state, expiry)
  -> purpose/context check
  -> recent-auth check when x-recent-auth
  -> rate/cooldown admission
  -> use case transaction
  -> typed response or Failure envelope
```

The error handler maps domain failure kinds to the approved code/status. It never
lets an exception message reach the body. `Retry-After` is set from
`retryAfterSeconds`.

## 8. Rate, cooldown and source identity

- `SourceIdentityResolver` defaults to the connection peer. Forwarded headers are
  ignored unless the peer is in `governance.trusted-proxies` (default empty).
- Trusted `X-Forwarded-For`: at most 8 IP literals, no ports, right-to-left to the
  first untrusted hop; all-trusted uses the leftmost. Malformed values are a
  request failure, not a fallback.
- Exact rolling windows `(now - window, now]` from `rate_event`; no fixed-window
  approximation.
- Cooldown is derived from failed full authentications only: 0/2/30/300 seconds
  at 1–4/5–9/10–19/20+. Rate/service/queue errors are not credential failures.
- Denial returns 429 with `Retry-After`; the server never sleeps a request thread.
- Bucket caps are enforced before accepting a new key; a full state returns 503,
  never evicts live protection.

## 9. Hash admission

`HashWorkLimiter` owns one worker thread and a four-slot queue:

- `submit` is rejected when the queue is full → 503.
- Caller waits at most two seconds for the result; timeout → 503, and the running
  job keeps the single permit until it ends.
- A late result cannot create a session; authority is checked at commit.
- Metrics expose queue depth/active count without identity labels.

## 10. Mail pipeline

- Admission inserts one `mail_request` in the use-case transaction and issues the
  link atomically when eligible. Ineligible requests get the generic 202 and no
  mail.
- Worker takes a global advisory lock, selects one due row with
  `FOR UPDATE SKIP LOCKED`, rechecks link/account state in the same transaction,
  then sends outside the transaction with a 10-second timeout.
- Three attempts, waits of 60 then 240 seconds; stop on consumption, expiry,
  supersession, disablement or attempt exhaustion.
- Delivery failure never revives a link and never changes the public response.
- Mailpit is the acceptance SMTP sink; production uses a configured relay.

## 11. Frontend design

- `AuthProvider` calls `readAuthContext` once at boot, keeps the CSRF token in
  memory, and exposes `anonymous | setup | human`.
- `client.ts` adds `X-CSRF-Token`, sends same-origin credentials, parses the
  `Failure` envelope, and maps codes to the exact copy in `07`.
- Route guards follow the approved redirect table; no protected shell renders
  before context resolves.
- `copy.ts` is the single frontend source for user-visible strings approved in
  `07`. It is not duplicated in components.
- Secret screens stop tracing/video before rendering; the harness owns capture
  state, not the app.
- The step-up dialog is reusable for password change, replacement and
  regeneration.

## 14. Harness design

- `tests/support/stack.ts` starts PostgreSQL and Mailpit if not running, applies
  Flyway through the app, and starts backend + frontend with test profile.
- One schema per worker; drop/recreate between workers.
- `tests/support/clock.ts` calls the loopback-only control channel with the
  per-run token.
- `tests/support/mail.ts` reads Mailpit by recipient and extracts the one-time
  token; it never stores the token in an artifact.
- `tests/support/secrets.ts` generates passwords, TOTP seeds and recovery
  codes per case.
- `tests/support/host.ts` spawns `arg-admin` with the test database and a
  temporary operator identity.
- `tests/support/recording.ts` stops Playwright tracing around secret displays.

## 15. Risks and open design questions

1. **Test clock channel.** Approved, but it is a test-only privilege boundary.
   Implementation must hard-disable it when the profile is not `test`.
2. **Operator identity on Windows.** Resolved by DR-040: the demo verifies the
   configured OS user; real group ACLs are documented as deployment-specific.
3. **jOOQ vs Spring JDBC.** Baseline allows either; this design chooses Spring
   JDBC to avoid code generation before the schema stabilizes.
4. **Spring Boot 4.1.2 pin.** Metadata only; re-verify at scaffold.
5. **PostgreSQL 18.6 install form.** Resolved by DR-040: project-local real
   PostgreSQL binaries, not an embedded classpath database.
6. **`scope_id` creation.** Created inside `completeEnrollment` on first
   completion only; host recovery never creates or reassigns it.

## 17. Phase 6 resolutions (DR-040)

| Conflict | Resolution |
|---|---|
| `readEnrollment` with no operation | 404 `NOT_FOUND`; contract `0.2.1`; UI starts a new operation |
| Host operator proof on Windows | Configured local OS user for the demo; group ACL deployment-specific |
| `__Host-` cookie on loopback | Try `http://localhost`; fall back to local HTTPS with a generated test certificate |
| PostgreSQL install form | Project-local PostgreSQL 18.6 binaries under `.local-tools` |
| Mail capacity | Count `PENDING`, `DELAYED`, `SENDING`, `INELIGIBLE_ACCEPTED`; terminal rows excluded |
| `host_audit.changed_fields` | JSONB array in DB, JSON array in CLI output |
| Manual-key/recovery locators | Labelled `<output>`/`<p>`/`<ol>`; no `data-testid` |
| Step-up retry | Re-issue the same request; server current-state/idempotency guards |

These resolutions are implementation detail unless they change an observable
contract; the `readEnrollment` 404 is the only contract change and is recorded in
`0.2.1`.
